# Smart AIO記事制作

OpenAI APIを使わず、現在のCodexまたはChatGPTの会話内で企画と本文を作成する。保護プロンプトは変更せず、新システムの情報を別のコンテキストとして扱う。

## 5段階の実行順序

1. **KW選定と調査**: 検索実測、候補KW、上位構成、読者の疑問を記録する。実測日と根拠がない候補は次へ進めない。
2. **独自性・タイトル・骨子**: 同じ顧客の過去記事、公式サイトの公開記事、一次情報から事例・視点・結論・見出しを先に確定する。[記事タイトル品質基準](references/title-quality.md)に従い、検索意図と責任ラベルから異なる切り口を内部で5案作り、具体性・信頼性・読者便益が最も高い1案だけを採用する。制作と別のAIによる `$article-quality-review` の `OUTLINE` レビュー合格を必須にする。公式サイトの公開記事と近い候補がある場合だけ、自動除外せず既存記事のタイトル・URL・一致理由を示し、利用者へ「このまま進める」「別記事にする」の2択を求める。重複ゲート後、記事の方向性、検索意図、責任ラベル、種別、ピラー、クラスター、タイトル、記事カテゴリ、ハッシュタグ、今回作る記事内容を `企画確認` タブへ出し、クライアントが承認した行のURL、行番号、承認ステータス、確認者、確認日を読み戻すまで本文作成へ進めない。
3. **執筆**: `$content-prompts` のSHA-256を確認し、保護プロンプトを一字も変更せず本文を作る。骨子を固め、企画確認シートの承認済み行を読み戻した後だけ執筆し、作りながら企画を変更しない。
4. **検品と裏取り**: 作成とは別のレビュー実行で、誤字、数値、固有名詞、禁止表現、出典、Web上の一次情報を確認する。未確認の主張が1件でもあれば仕上げへ進めない。
5. **仕上げと最終承認待ち**: 同じ顧客の内部リンク網、構造化マークアップ、図解画像、記事内画像、アイキャッチを挿入する。内部リンクは `plan-internal-link-graph` で新記事から既存記事への発リンクと既存記事側への戻しリンク更新計画を作る。内部リンクの遷移先URLは記事一覧の `公開URL` を正本にし、既存運用の互換読み取りとして `WordPressURL` だけを参照してよい。`記事URL` やGoogleドキュメント/Drive URLを公開記事URLとして使ってはならず、公開URLが未入力の場合は `CONTENT_OPTIMIZATION_INTERNAL_LINK_PUBLIC_URL_REQUIRED` で停止する。発リンクは同じピラー・クラスター関係を目安に選び、本文中のテキストリンクではなくQ&A直後のHタグなし「関連記事」ラベル配下に記事タイトルリンクとして出す。`verify-internal-link-graph` には各発リンクの `placement.type=RELATED_ARTICLES_AFTER_QA`、`placement.after_qa=true`、`placement.section_label=関連記事`、`placement.section_is_heading=false`、`anchor_text`、`target_url` を渡す。Googleドキュメント本文ではURLだけの段落や裸URLを出さず、記事タイトルへネイティブリンクを付け、`article_document_readback.internal_links[].native_link_verified=true`、`bare_url_visible=false`、`after_qa=true` を確認する。記事本文とJSONに加えて `{記事ID}_schema.jsonld` を作り、`verify-structured-markup` で検証する。記事一覧の `メタディスクリプション` を正本にし、`Article.description` とWordPressコピペ用JSON-LDのdescriptionはこの列と完全一致させる。構造化マークアップには `Article`、`BreadcrumbList`、本文のQ&A 5件と完全同期した `FAQPage` を必ず含める。`Article.mainEntityOfPage` は公開記事URLにし、Drive/Docs URLは禁止する。構造化マークアップの `Article.author.name` は同じクライアントの基本情報にあるプロフィールウィジェット用編集部名を使い、`publisher`、`keywords`、アイキャッチ画像用の `image` は含めない。WordPress投入用の色付きブロックは、`この記事でわかること` の3箇条で1ブロック、`この記事の要約` は改行を残して1ブロック、`この記事のまとめ` も改行を残して1ブロック、`Q&A` は各Q&Aペアで1ブロック（合計5ブロック）にする。QとAを別ブロックに分けてはならない。図解画像は、本文内の図解対象箇所を `[DIAGRAM]...[/DIAGRAM]` で囲み、Googleドキュメント上で色付けしてから作る。図解対象箇所は、記事の前後文脈と自然につながる通常の説明段落にする。短文・項目の羅列、画像生成用メモ、キャプションだけの文章を図解対象にしてはならない。図解元本文は図解の読み方や意図の説明ではなく、図解画像にする内容そのものを本文として書く。図解プロンプトにはその本文抜粋と、図解内に入れる2〜6個の本文由来テキストまたは意味を変えない短いラベルを渡し、本文にない新しい概念・判断項目・追加説明は入れない。図解は元文章を見やすく変換するためだけに作り、本文と図解の項目・順序・意味が一致していることを検証する。図解は人が見やすいことを最優先し、企業ロゴ、アニメキャラクターなど著作権のあるもの、意味のないチェックマークだけの帯、余白埋めの記号列を入れない。背景は白または淡色の不透明背景にする。タイトル画像1枚と構図の異なる記事内写真3枚、さらに図解画像1枚を1536x1024のPNGで、現在の会話内の正規画像生成フローにより実生成し、`{記事ID}_1.png`〜`{記事ID}_4.png` と `{記事ID}_diagram_1.png` として顧客フォルダー配下の `04_画像/{記事ID}` フォルダーへ保存する。Googleドキュメント本文では色付けした図解元段落の直後に図解画像を置き、元文章と画像の両方を残す。PIL、ImageDraw、Image.new、ローカルPython、`build_articles.py`、テンプレート、プレースホルダー由来の画像は仮画像として扱い、記事画像の完了証拠にしない。Driveと記事一覧の `画像完成`・`画像URL`・`図解完成`・`図解URL` を再読込し、図解元本文の色付け、図解元本文が図解内容そのものである証拠、図解内テキストが本文由来である証拠、画像保存を `verify-article-visual-persistence` で検証してから、制作と別のAIによる `FINAL` レビューに合格させる。完成物だけを人へ提示し、同じ記事・版に対する1回の `FINAL_APPROVAL` 後だけ公開可能にする。

タイトル画像は記事タイトルの文字だけを読める文字として許可し、背景の看板、ポスター、端末画面、装飾、ロゴ風要素などには読める文字をできるだけ入れない。通常画像3枚も、看板、ポスター、端末画面、背景、装飾などに読める文字ができるだけ入らない構図にする。文字情報が必要な場合でも、具体的な日本語・英数字・ロゴ風文字は避け、無地または判読不能な抽象表示にする。この文字抑制ルールはタイトル画像の背景と本文写真・背景写真に適用し、図解画像には適用しない。

画像生成時は `prepare-images` が返した `content_prompt` を短縮・要約・手入力で置き換えず、そのまま現在の会話内の画像生成へ渡す。各画像には `generation_call_id`、準備済みプロンプトSHA、実際に生成へ使ったプロンプトSHA、プロンプト完全一致の証拠、実ファイルから測定した1536x1024の寸法証拠を残す。1枚目のタイトル画像は、記事タイトルを主見出しと補助見出しに分けて読みやすく配置し、背景の読める文字をできるだけ入れない。通常画像3枚も背景・看板・端末画面などの読める文字をできるだけ入れない。この文字抑制ルールは図解画像には適用しない。

タイトル画像生成後は、作成と異なる `review_run_id` の評価役が評価モデルを記録し、`inspection_method=ORIGINAL_IMAGE_VISUAL_INSPECTION` で原寸画像とID-00016相当の基準画像を比較する。タイトル文言の可読性、主見出しと補助見出しの階層、記事タイトルの保持、背景文字の抑制、ブログサムネイルとしての完成度、日本語の誤字なし、著作権安全性を証拠化し、85点未満、タイトル階層不明、背景文字が目立つ、タイトルの欠落・改変のいずれかなら保存工程へ進まない。

図解生成後は、作成と異なる `review_run_id` の評価役が評価モデルを記録し、`inspection_method=ORIGINAL_IMAGE_VISUAL_INSPECTION` で原寸画像とID-00016相当の基準画像を比較する。図解SHA、タイトルまたは文脈見出し、補足文、視線誘導、情報階層、65〜95%の画面利用、読める日本語、誤字なし、判断結果または結論、本文忠実性、著作権安全性を証拠化し、85点未満、低密度、項目名とアイコンを並べただけ、必須項目欠損、本文にない文字・数値・説明の追加のいずれかなら保存工程へ進まない。問題点を1回の生成につき1〜3点に絞って再生成し、別SHAで再レビューする。

Drive保存、画像保存、記事制作シート更新まで完了した記事を利用者へ報告するときは、記事本文、Drive格納先フォルダー、画像フォルダー、図解画像、構造化マークアップ、更新した記事制作シートのURLを必ず提示する。Googleドキュメントは保存後に再読み込みし、センチネル置換後の読み戻し本文と期待本文の正規化文字数・SHA-256が一致し、同じ文書IDが対象記事フォルダー内にある場合だけ完成扱いにする。URLだけ揃った状態を記事完成として扱わない。

全段階で `$smart-aio-intake` と `$client-context` により `client_id`、制作AI、独立レビューAI、最終承認者、保存先を固定する。人の氏名は完成物を承認した時点で監査記録へ保存する。保護プロンプトへ一次情報や新ルールを追記せず、`context_packet` と段階ゲートを外側に持たせる。

`記事一覧` へ書く前に毎回ヘッダー行全体を読み、実際のヘッダー配列を `article_headers` としてランタイムへ渡す。列文字を固定してはならない。標準32列と、既存シート互換のため先頭に空列が1つある33列配置だけを許可し、ヘッダー名から書込列を解決する。

担当者の操作面と記事データの正本は、SMARTAIO本番Drive直下クライアントフォルダーの `記事制作シートURL` が示すクライアント別シートとする。`基本情報`、`企画確認`、`記事一覧`、`キーワード`、`クラスター`、`設定` の6シートとシステム契約の列順を表示し、記事案、承認状態、完了日、記事URL、画像URL、WordPress URLをそのシートへ戻す。`基本情報` にはプロフィールウィジェット用のサイト名、編集部名、編集チーム説明を保持し、同じクライアント内の記事の `author.name` に同じ編集部名を使う。`企画確認` は1行目へ `制作順`、`確認ID`、`記事トピック`、`種別`、`ピラー`、`クラスター`、`記事タイトル案`、`対策キーワード`、`検索意図`、`AI引用戦略`、`記事カテゴリ`、`ハッシュタグ`、`確認ステータス`、`確認者`、`確認日`、`修正コメント`、`制作状態`、`記事ID`、`記事URL`、`最終更新日` を置く。`種別` は `ピラー` または `クラスター` のみとし、ピラーは親テーマ、クラスターはピラーから派生する子テーマを示す。クライアントは `確認ステータス`、`確認者`、`確認日`、`修正コメント` を編集し、システムは `制作順`、`確認ID`、`制作状態`、`記事ID`、`記事URL`、`最終更新日` を管理する。記事作成依頼時は `select-next-approved-plan` で `確認ステータス` が `承認` / `OK` / `APPROVED`、かつ未制作の行を `制作順` 昇順で1件だけ選び、`validate-plan-confirmation-candidates` の正式な重複判定を通してから本文制作へ渡す。承認済み50案が完了した後に追加依頼があれば、`prepare-additional-plan-confirmation-ideas` で既存企画・記事一覧・クラスター・公式サイト記事との重複判定を通した次の50案を追記する。`記事一覧` と `クラスター` は1行目へ一覧名、2行目へシステム契約のヘッダーを置く。`キーワード` は候補・検索数・難易度を保持し、`クラスター` では右側にピラー一覧も同時表示する。中央管理台帳は索引・監査用であり、記事行の入力先にはしない。

## コマンド

入力JSONの項目は [記事制作契約](references/article-contract.md) に従う。

```bash
node scripts/article_workflow.mjs prepare-idea input.json
node scripts/article_workflow.mjs prepare-article input.json
node scripts/article_workflow.mjs analyze input.json
node ../smart-aio-orchestrator/scripts/smart_aio_orchestrator.mjs create-article-lifecycle input.json
node ../smart-aio-orchestrator/scripts/smart_aio_orchestrator.mjs advance-article-lifecycle input.json
node ../smart-aio-orchestrator/scripts/smart_aio_orchestrator.mjs prepare-plan-confirmation-sheet input.json
node ../smart-aio-orchestrator/scripts/smart_aio_orchestrator.mjs validate-plan-confirmation-candidates input.json
node ../smart-aio-orchestrator/scripts/smart_aio_orchestrator.mjs select-next-approved-plan input.json
node ../smart-aio-orchestrator/scripts/smart_aio_orchestrator.mjs prepare-additional-plan-confirmation-ideas input.json
```

記事案作成前は `plan-idea` で、指定トピックがあれば最優先し、次に指定ピラー、どちらもなければ登録順の次ピラーを選ぶ。生成時は保護プロンプト正本の後ろへ `title-refinement-v1` を追加し、正本文を改変せずタイトル品質を強化する。生成後は `validate-ideas` で責任ラベル、近接検索意図、タイトル品質、古い年号、カテゴリ、ハッシュタグ、スラッグを検査する。タイトルは70点未満、22文字未満、58文字超、根拠のない煽り表現のいずれか、またはハッシュタグ未入力で再生成する。失敗時は最大3回まで、返された `retry_errors` を変更せず `prepare-idea` の `retryErrors` へ渡して再生成する。検査合格後は `AWAITING_ARTICLE_PLAN_CONFIRMATION` として、`企画確認` タブに確認用行を作る。行には `記事トピック`、`種別`、`ピラー`、`クラスター`、`記事タイトル案`、`対策キーワード`、`検索意図`、`AI引用戦略`、`記事カテゴリ`、`ハッシュタグ` を入れ、クライアントが `確認ステータス` を `承認` / `OK` / `APPROVED` にしたことを読み戻した後だけ `finalize-idea` で歯抜け行を考慮した `ID-00001` 形式のID、記事IDフォルダー、JSON、記事一覧の `ピラー` から `JSON_URL` までと `タイトルスラッグ`、記事本文プロンプトを一体で準備する。

記事カテゴリは `基本情報` の登録済み20カテゴリを正本とし、記事企画の開始時に20件すべてのカテゴリ名とカテゴリスラッグを必須入力とする。20件が揃わない場合は `ARTICLE_CATEGORY_REGISTRY_REQUIRES_20` で停止する。`articleCategory` へカテゴリ名を完全一致で1つだけ入れ、語順変更、表記揺れ、似た別カテゴリの自動作成を許可しない。カテゴリ名から登録済みカテゴリスラッグを解決できない場合は `RETRY_REQUIRED` とし、記事一覧へ書かない。記事スラッグは `タイトルスラッグ` へ保存する。完全な想定公開URLは、公開先ドメインとWordPressのパーマリンク構造が両方設定された場合だけ生成する。WordPress投稿後はAPIが返した正式URLを `公開URL` 列へ記録し、既存運用互換が必要な場合だけ同じ値を `WordPressURL` にも残す。内部リンク、構造化マークアップ、`Article.mainEntityOfPage` は `公開URL` を正本にする。

記事一覧へ書く直前に、同じ記事IDの既存タイトルと責任ラベルを必ず読む。既存IDへ別企画を上書きせず、内容が異なる場合は新しい記事IDを採番する。承認済みIDの再利用・付け替えは禁止する。記事一覧には構造化マークアップ、図解、内部リンク状態、リライト状態も標準列として記録する。

新規採番前に、同一顧客の記事制作シートの `記事一覧` と `クラスター` にある全記事IDを読み、通常運用ではゴミ箱内成果物から確認した廃止済み記事IDを `retired_article_ids` として加え、現行IDと廃止済みIDの最大番号より大きいIDを使用する。先頭行が空いていても、通常運用では既存IDまたは廃止済みIDが1件でもあれば `ID-00001` へ戻さない。利用者が「フォルダーを削除して最初から」「一から通常フローで実行」など全削除・作り直しを明示し、新しい制作シート内に有効記事IDがない場合だけ、`article_id_sequence_mode=RESET_FROM_ONE_AFTER_EXPLICIT_REBUILD` と `explicit_full_rebuild_confirmed=true` を渡し、廃止済みIDを採番計算から外して `ID-00001` から開始してよい。この場合も現行シート内の有効記事IDは衝突防止のため必ず採番計算へ含める。過去記事のタイトル・責任ラベル・検索意図は重複判定へ必ず含める。廃止済み記事の本文やURLは重複判定・内部リンク・保存先へ流用しない。

公式サイトのサイトマップ、記事一覧、サイト内検索から取得した公開記事は `publishedSiteArticles` として、同一顧客の `client_id`、タイトル、URL、取得できる場合は検索意図を保持する。公式サイト一致は削除・除外・自動再生成の理由にしない。`SITE_DUPLICATE_DECISION_REQUIRED` を返し、利用者が `PROCEED_AS_NEW` を選べば一致情報と選択履歴を残して制作を続け、`CREATE_ALTERNATIVE` を選べば `ALTERNATIVE_ARTICLE_REQUIRED` として検索意図・責任範囲の異なる企画を作り直す。選択がないまま本文生成へ進めない。

記事ID JSONへ保存する `articlePrompt` は、`$content-prompts` の `article-writing` と記事データだけで構成する。責任ラベル遵守ルールはJSONへ重ねて保存せず、本文を生成する直前の `prepare-article` で一度だけ追加する。記事案プロンプトへ渡す過去記事は `title` と `responsibilityLabel` だけに限定し、新システムの顧客ID、内部メモ、保存先は混ぜない。

複数記事処理は `create-batch` で開始し、`batch-next` で `ピラー`、`記事URL`、`画像URL` の状態に基づく処理優先順位を取得する。成功は `apply-batch-step`、失敗は `fail-batch-step` へ記録し、`stop-batch` と `resume-batch` で停止・再開する。最終ステップ成功時は同じ処理内で完了状態へ移す。

自動リライトは `prepare-rewrite-plan` で同じ顧客の順位・クリック・表示回数・検索意図変化から候補を抽出する。候補化と下書き作成は自動化できるが、既存公開記事の更新やWordPress反映は `FINAL_APPROVAL` または更新承認なしに実行しない。

クラスター一覧は `prepare-cluster` で未処理記事を最大20件ずつ準備し、会話内生成後に `complete-cluster` で `記事ID` から `AI引用戦略` までの行へ変換する。

## 停止条件

- `client_id` がない、または記事、一次情報、過去記事の顧客が一致しない。
- `production_sheet_url` がない、6シートまたは `system-contract.mjs` の列構成が一致しない。
- `retired_article_ids` が未取得、配列でない、または `ID-00001` 形式でない。廃止済みIDを無視して `ID-00001` から開始する場合は、利用者の全削除・作り直し指示と `explicit_full_rebuild_confirmed=true` がない。
- 保護プロンプトのチェックサムが一致しない。
- クライアント別記事制作シート内で、同一タイトル、同一指紋、責任ラベル重複がある。
- 公式サイトに近い公開記事があり、「このまま進める」「別記事にする」の選択がまだない。
- 記事の方向性、検索意図、責任ラベル、タイトル、記事カテゴリ、ハッシュタグ、今回作成する記事内容について、`企画確認` タブの承認済み行がまだない。
- ハッシュタグが未入力、または記事制作シートと記事ID JSONで一致しない。Googleドキュメント本文に「タグ」「出典」「参考情報」セクションが表示されている。
- 記事企画・骨子が独立AIレビューに合格していない。
- タイトル品質が70点未満、長さが22〜58文字の範囲外、または根拠のない煽り表現を含む。
- 記事カテゴリが `基本情報` の登録済みカテゴリ名と完全一致せず、カテゴリスラッグを解決できない。
- `基本情報` の登録済み20カテゴリが記事企画入力へ渡されていない、またはカテゴリ名・スラッグが空欄・重複・不正形式である。
- 利用不可または期限切れの一次情報しかない。
- 検索実測、独自性、骨子レビュー、事実確認、最終レビューのいずれかが未完了。
- 作成実行とレビュー実行のIDが同じ。
- 内部リンク網が `verify-internal-link-graph` に合格していない。既存記事があるのに新記事からの発リンクが0件、既存記事側への戻しリンク更新計画がない、Q&A直後のHタグなし「関連記事」ラベル配下の記事タイトルリンクになっていない、記事一覧の `公開URL` または互換用 `WordPressURL` に公開記事URLがない、Drive/Docs URLを遷移先にしている、または本文中のテキストリンク・タグ・出典セクションとして出している。
- 構造化マークアップ出力物が作成・保存・検証されていない。`{記事ID}_schema.jsonld`、`Article`、`BreadcrumbList`、本文Q&A 5件と同期した `FAQPage`、`keywords` とアイキャッチ画像用 `image` の不在、Drive記事フォルダー所属、記事一覧の `メタディスクリプション` と `Article.description` の完全一致、記事一覧の `構造化完成`・既存列 `構造化URL` 再読込が揃わない。
- タイトル画像1枚、通常画像3枚、図解1枚が現在の会話内の正規画像生成フローで実生成・保存されていない、同じ画像内容が重複している、`{記事ID}_1.png`〜`{記事ID}_4.png` と `{記事ID}_diagram_1.png`・PNG・1536x1024の規則と一致しない、1枚目のタイトル画像に記事タイトルが入っている証跡がない、図解元本文が `[DIAGRAM]...[/DIAGRAM]` で色付けされていない、図解元本文が図解内容そのものではなく図解の説明文になっている、図解内テキストが本文抜粋由来の概念から外れている、図解SHAに結び付いた独立視覚品質レビューがない、図解品質85点未満、画面利用率65〜95%外、低密度、項目名とアイコンの単純列、`04_画像/{記事ID}` へのDrive所属または記事一覧の `画像完成`・`画像URL`・`図解完成`・`図解URL` を再読込していない。
- タイトル画像の背景または通常画像3枚について、読める文字をできるだけ避ける指示と確認証拠がない。またはタイトル画像の背景や通常画像に、記事タイトル以外の具体的な日本語・英数字、ロゴ風文字を意図的に入れている。この停止条件は図解画像には適用しない。
- PIL、ImageDraw、Image.new、ローカルPython、`build_articles.py`、テンプレート、プレースホルダー由来の画像を記事画像として保存・報告しようとしている。
- Googleドキュメントを再読み込みしていない、読み戻しセンチネルが置換されていない、期待本文と読み戻し本文の正規化文字数・SHA-256が一致しない、または同じ文書IDを対象記事フォルダー内で確認できない。

別顧客の記事を参考例として表示したり、リンク候補へ混ぜたりしない。
